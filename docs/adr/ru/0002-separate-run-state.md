# ADR-0002: Состояние запусков в отдельных локальных файлах

[English](../0002-separate-run-state.md) · Русский

- Статус: принято
- Дата: 2026-11-20

## Контекст

Агенту нужно помнить последний запуск, последний успешный backup, результаты check и verify, короткую историю, окна дедупликации алертов и локальную блокировку. Репозиторий принадлежит restic и должен оставаться стандартным репозиторием restic, читаемым без JealousVault. База данных добавила бы сервис, схему и ещё один режим отказа инструменту, который и так работает от root.

## Решение

Хранить служебные данные в небольших локальных файлах в `/var/lib/jealous-vault/`, а audit-журнал - в `/var/log/jealous-vault/`:

- `state.json` для последних результатов, атомарная запись с режимом `0600`;
- `history.jsonl` и `audit.jsonl` как append-only JSONL;
- `backup.lock` для `flock` и диагностики держателя;
- `alerts.json` для окон дедупликации.

Испорченный state переносится в `state.json.corrupt-<timestamp>` и считается пустым, чтобы повреждённый файл служебных данных не останавливал будущие backup.

## Последствия

- Нет базы данных, демона и дополнительного порта.
- Репозиторий остаётся переносимым: потеря локального state не теряет данные backup.
- State привязан к хосту и job; запроса по многим хостам нет. Статус флота - отдельный будущий продукт.
- Обновления могут перезаписывать `state.json`; им владеет агент, это не пользовательская база.
- Ротация и ретенция history - простые файловые операции, а не политика в БД.

## Рассмотренные альтернативы

- **SQLite**: зависимость и схема без реальной потребности в запросах; всё равно локальный файл, который можно повредить.
- **Хранить state в репозитории restic**: смешивает метаданные агента с данными backup и ломает обещание, что репозиторий остаётся обычным репозиторием restic.
- **PostgreSQL/MySQL**: ещё один сервис, который нужно ставить, защищать и мониторить на каждом хосте.
- **Совсем без state**: нет проверки свежести, дедупликации и команд `status`/`history`.

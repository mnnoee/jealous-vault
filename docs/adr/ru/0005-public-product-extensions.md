# ADR-0005: Публичный продукт с независимыми расширениями

[English](../0005-public-product-extensions.md) · Русский

- Статус: принято
- Дата: 2026-11-20

## Контекст

JealousVault поддерживает один человек, и проект должен оставаться устойчивым. Код под Apache-2.0, и эта лицензия необратима: всё опубликованное в этом репозитории остаётся открытым. Пользователи backup-инструмента особенно чувствительны к пейволам вокруг restore и сохранности данных.

Модель open core с платным слоем для базовых возможностей создала бы искусственную границу и поставила бы под риск доверие. При этом расширения, интеграции, хостинговые сервисы и поддержка - естественные вещи для коммерческого предложения, а сторонние разработчики могут захотеть делать плагины под своими лицензиями.

## Решение

Публичный репозиторий содержит полный продукт под Apache-2.0 без искусственных ограничений функциональности. Это не урезанная freemium-редакция.

Коммерческая работа дополняет его и отделена:

- расширения, плагины, интеграции с чатами, центральный web UI, хостинговые сервисы и поддержка;
- отдельные репозитории и отдельные лицензии;
- права на работу остаются у авторов, включая сторонние плагины под GPL-3.0 или другой лицензией;
- публичный продукт никогда не урезается, чтобы коммерческое расширение выглядело лучше.

Вклады в публичный репозиторий требуют только подписи DCO и принимаются под Apache-2.0. Они не предоставляют дополнительных проприетарных прав.

Отдельное письменное соглашение [CLA.ru.md](../../../CLA.ru.md) используется только когда mnnoee принимает код контрибьютора в коммерческое расширение. В нём лицензиатом указан mnnoee, есть лицензия на объекты авторского права и патентная лицензия, определено, что считается Вкладом, и сказано, что последующие соглашения не отменяют ранее выданные разрешения.

## Последствия

- Проекту не нужно владеть кодом контрибьюторов, чтобы использовать его; Apache-2.0 уже разрешает коммерческое использование, форки и совместимые продукты.
- Платное предложение должно быть действительно дополнительной работой, а не удержанной частью публичного продукта.
- Конкуренты могут форкнуть публичный продукт и предложить свою поддержку или расширения. Это приемлемо; проект конкурирует качеством, а не шлагбаумом.
- Экосистема может включать плагины под GPL-3.0 и альтернативные реализации. Документированные CLI, конфиг и JSON-вывод - стабильная поверхность интеграции.
- CLA нужен только для авторов коммерческих расширений, поэтому трение для обычных pull request остаётся низким.
- Названию и логотипу нужны ясные правила, чтобы сторонняя работа не создавала впечатление официального одобрения.

## Рассмотренные альтернативы

- **Open core с платными базовыми возможностями**: отклонено, потому что создаёт искусственную границу, провоцирует проблемы доверия вокруг restore и security и делает публичный продукт неполным.
- **Закрытый исходный код**: отклонено; теряется проверяемость, ручной выход через restic и возможность убедиться, что restore работает.
- **Только пожертвования**: совместимо с лицензией, но не надёжный способ финансировать поддержку и интеграции.
- **CLA для каждого вклада**: отклонено; добавляет лишнее трение, а Apache-2.0 уже позволяет проекту и другим использовать код коммерчески.

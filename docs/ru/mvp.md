## Рамка продукта

JealousVault - открытый проект, а не продукт за шлагбаумом.

- Публичный продукт - это полный backup-инструмент под Apache-2.0. Это не урезанная freemium-редакция и в нём нет feature gate.
- Коммерческая работа дополняет его: расширения, плагины, интеграции, хостинговые сервисы, поддержка и заказная разработка. Она не убирает возможности из публичного продукта.
- Любой может форкнуть публичный продукт, запускать его на любом числе хостов или построить совместимую реализацию. Лицензия это разрешает; проект это не одобряет.
- Проект поддерживает один человек, поэтому публичный продукт должен оставаться достаточно малым, чтобы его можно было доделать, протестировать и сопровождать.

Успех для backup-инструмента узкий и строгий: один сценарий должен работать, а restore должен быть доказан. Возможность, которую нельзя восстановить, не считается возможностью.

## Публичный продукт

| Область        | Что входит                                                                           |
| -------------- | ------------------------------------------------------------------------------------ |
| Один хост      | backup, check, prune, restore                                                        |
| Планировщики   | systemd, cron, OpenRC, runit, `tick`                                                 |
| Хранение       | local, SFTP, S3-совместимое (включая Backblaze B2), REST                             |
| Базы данных    | PostgreSQL, MySQL/MariaDB                                                            |
| Базовые алерты | email, Telegram, JSON webhook, healthchecks-совместимый ping                         |
| Проверки       | `doctor`, `history`, `test-restore`, блокировки, audit-журнал                        |
| Restore drill  | `drill --level files/service/db/full`, JSON-отчёт, history                           |
| Ручной выход   | `export-restic-env`, recovery kit, документированные команды restic, примеры конфига |
| Документация   | install, configuration, operations, restore, limits, troubleshooting                 |

Публичный продукт никогда не урезается, чтобы коммерческое расширение выглядело лучше. Restore, проверки целостности, security-исправления, базовые алерты и документация остаются в нём.

## Коммерческие дополнения

Это отдельные продукты или услуги. Они могут жить в отдельных репозиториях с отдельными лицензиями, а права на работу их авторов остаются у авторов.

| Область                | Примеры                                                           |
| ---------------------- | ----------------------------------------------------------------- |
| Центральное управление | web UI и статус для флота хостов                                  |
| Интеграции с чатами    | коннекторы Slack и Discord                                        |
| Хостинговые сервисы    | relay алертов, managed-хостинг репозитория                        |
| Compliance             | PDF/CSV-отчёты и экспорт доказательств                            |
| Учения на флоте        | restore-учения по многим хостам с единым хранилищем доказательств |
| Корпоративный доступ   | SSO, RBAC, экспорт аудита, интеграции с тикет-системами           |
| Поддержка              | приоритетная поддержка, консультации, заказная разработка         |
| Коммерческие лицензии  | платные лицензии на расширения проекта                            |

Коммерческое дополнение может использовать документированные CLI, конфиг и JSON-вывод. Оно не должно быть обязательным для работы публичного продукта.

## Определение MVP

Для backup-инструмента MVP значит: **один happy path работает от начала до конца, и restore доказан.**

Golden path:

```text
S3 (основной) или local (тесты)
  -> дамп PostgreSQL
  -> systemd-таймер
  -> алерт в Telegram
  -> restore на чистый хост
  -> count/sum совпадает
```

Путь должен быть отполирован. Пять бэкендов, работающих по чуть-чуть, хуже одного, работающего предсказуемо.

### Критерии приёмки

1. Один golden path описан и проверен: S3 или local, PostgreSQL, systemd, Telegram, restore, diff.
2. Интеграционный тест restore идёт в CI с настоящим restic, а не с заглушкой.
3. Установка одной командой на двух дистрибутивах: `deb` плюс `AUR` или `rpm`.
4. Схема конфига версионирована, а `config migrate` обновляет старый файл.
5. `export-restic-env` (или эквивалентная однострочная команда) даёт ручной выход без агента.
6. Незнакомый человек проходит install -> configure -> backup -> restore -> troubleshooting, не спрашивая мейнтейнера.
7. Ограничения явные: что проверено, что нет и на каких версиях. Канонический документ - [platforms-and-limits.md](platforms-and-limits.md), ссылка на него есть в начале README.

### Текущее состояние относительно критериев

| Критерий                 | В 0.1.2                                                             | Чего не хватает                                     |
| ------------------------ | ------------------------------------------------------------------- | --------------------------------------------------- |
| Golden path              | Работает вручную и через `.deb` на живых хостах, S3 и PostgreSQL   | Нет `rpm`/`AUR`; нет единого пути для всех дистрибутивов |
| Restore-тест в CI        | Unit-тесты используют fake restic; drill/test-restore покрывают путь; настоящий restic проверен вручную в LXC | Нет job с настоящим restic в CI |
| Установка одной командой | Бинарный ассет, `jealous-vault install` и пакет `.deb`              | Нет пакетов `rpm`/`AUR`                             |
| Версионированная схема   | Строгий TOML, неизвестные ключи отвергаются                         | Нет версии схемы и `config migrate`                 |
| Ручной выход             | `export-restic-env` выводит переменные, команды и учёт дампов       | Покрыто                                             |
| Незнакомец проходит путь | Документация покрывает путь                                         | Путь ещё не проверен на стороннем человеке          |
| Явные ограничения        | [platforms-and-limits.md](platforms-and-limits.md)                  | Держать ссылку с README и обновлять                 |

## Не входит в MVP

- второй бэкенд хранения сверх golden path;
- второй планировщик сверх systemd для golden path;
- второй канал алертов сверх Telegram для golden path;
- центральный web UI, управление флотом или сервер;
- интеграции Slack/Discord и другие коммерческие расширения;
- SSO, RBAC, compliance-отчёты;
- поддержка Windows;
- кластер Proxmox и очень большие `vzdump`-архивы;
- managed hosting.

От этого не отказываются навсегда. Это отложено, пока golden path и доказательство restore не станут скучными. Расширения живут вне этого репозитория и не блокируют публичный продукт.

## Правило для новых возможностей

Задайте один вопрос: **усиливает ли это golden path или доказательство restore?**

- Если да, это может войти в MVP.
- Если нет, ждёт выполнения критериев MVP.
- Если это расширение или коммерческая функция, в этот репозиторий она не входит вообще; ей место в отдельном репозитории с собственной лицензией.

Каждая новая интеграция - код, который один человек должен протестировать, описать и чинить. Ответ по умолчанию - нет.

## Доказательства

Утверждение об MVP требует доказательства, а не намерения:

- прогон CI или воспроизводимый тест;
- хост, дистрибутив и версия restic;
- точный результат restore, например `count/sum` до и после;
- запись в changelog, когда меняется поведение.

«Должно работать» доказательством не является.

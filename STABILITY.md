# Stability and compatibility

English · [Русский](STABILITY.ru.md)

This document is the compatibility contract for JealousVault. It defines what is public, what may
change, and how much warning users get. Anything not listed as public here is internal.

The contract applies to the latest stable release. Prereleases, beta tags and builds from `master`
are for testing and make no compatibility promise.

Commercial extensions are separate products. Their licences, release cycles and support terms are
not part of this contract.

## Versioning

JealousVault follows semantic versioning: `MAJOR.MINOR.PATCH`.

- `PATCH`: compatible fixes, documentation and internal changes.
- `MINOR`: new features and compatible additions to the public API.
- `MAJOR`: breaking changes.

The project is below `1.0.0`. Before `1.0.0`, a `MINOR` release may break compatibility, but only
deliberately: the change must be listed in [CHANGELOG.md](CHANGELOG.md) under `Changed` or `Removed`
and, where technically possible, the old form must keep working for at least one `MINOR` release.
Silent breaks are bugs.

Security fixes may break compatibility without the usual deprecation window when keeping the old
behaviour would keep users at risk. Such changes are marked in the changelog.

## Public API

### CLI

Public:

- command names and subcommands: `init`, `repo`, `install`, `uninstall`, `backup`, `vzdump`,
  `restore-vm`, `snapshots`, `mount`, `restore`, `test-restore`, `check`, `doctor`, `freshness`,
  `status`, `history`, `tick`, `recovery-kit`, `version`;
- flags documented in `--help` and in `docs/`;
- exit codes: `0` for success, `1` for any failure (bad config, runtime error, failed check, stale
  backup);
- `--json` output for the fields documented in `docs/`; new fields may be added.

Internal:

- exact human-readable wording of errors, logs and alerts;
- progress output, colours and the order of help sections;
- performance, memory use and the number of restic calls.

Parse stdout only where `--json` is documented. Logs on stderr are for humans and may change.

### Configuration

Public:

- file locations: `/etc/jealous-vault/config.toml` and `/etc/jealous-vault/<job>.toml`;
- every TOML key, default and accepted value documented in
  [docs/configuration.md](docs/configuration.md);
- validation rules, including rejection of unknown keys;
- multiple jobs and the per-job state, cache and unit naming rules.

Internal:

- comments and key order in the config generated by `init`;
- the wording of validation errors.

Adding a key with a safe default is compatible. Renaming or removing a key, changing its meaning, or
changing a default that affects backup content is breaking.

The config has no version field. Unknown keys are a hard error, so an older binary rejects a newer
config instead of silently ignoring a setting. This is deliberate: a typo must not disable a backup.
There is no `config migrate` command yet; until it exists, read the changelog before upgrading.

### State, history and audit

These files are written by the agent with mode `0600`:

| File            | Format | Purpose                              |
| --------------- | ------ | ------------------------------------ |
| `state.json`    | JSON   | last backup, check and verify result |
| `history.jsonl` | JSONL  | append-only run history              |
| `audit.jsonl`   | JSONL  | append-only critical-action journal  |
| `backup.lock`   | JSON   | lock holder, diagnostics only        |
| `alerts.json`   | JSON   | alert deduplication windows          |

`state.json` has four optional keys: `last_run`, `last_success`, `last_check`, `last_verify`. Each
holds a run object with these fields: `kind`, `started_at`, `finished_at`, `status`, `snapshot_id`,
`files_new`, `files_changed`, `bytes_added`, `duration_seconds`, `warnings`, `error`. `kind` is
`backup`, `check` or `verify`; `status` is `success`, `failed` or `skipped`.

`history.jsonl` contains one run object per line, oldest first. A torn last line is ignored; a
malformed line in the middle is an error.

`audit.jsonl` contains one entry per line with at least `ts`, `action`, `user`, `uid`, `host` and
`result`. Actions include `backup`, `restore`, `check`, `verify`, `repo.init`, `repo.unlock`,
`repo.delete`, `repo.copy`, `install`, `uninstall` and `mount`. Extra fields such as `snapshot`,
`target`, `source` and `error` may be present.

Guarantees:

- the documented field names, types and meanings are stable;
- new fields may be added, so readers must ignore unknown fields;
- the agent owns these files: an upgrade may rewrite `state.json` and append to the journals;
- do not store your own data in them and do not edit them by hand;
- a corrupt state file is quarantined as `state.json.corrupt-<timestamp>` and treated as empty.

Breaking: removing or renaming a documented field, changing its meaning, or changing the line
format. Changing rotation limits (currently 4 MiB and 2000 runs for history) is not breaking.

`backup.lock` is public only for diagnostics. It is JSON with `pid`, `command` and `started_at`;
exclusion is done with `flock`, not by the file contents. Do not delete a lock while a run is
active. Stale locks are cleared by `backup` and `check`.

### systemd units and scheduler entries

Public unit names:

- `jealous-vault-backup.service` / `.timer`
- `jealous-vault-check.service` / `.timer`
- `jealous-vault-verify.service` / `.timer`
- `jealous-vault-freshness.service` / `.timer`
- `jealous-vault-copy.service` / `.timer`
- `jealous-vault-proxmox.service` / `.timer`

The default job has no suffix. Other jobs get `-<job>`, for example
`jealous-vault-backup-usr.timer`. OpenRC and cron entries use the same base names.

Public: unit names, the job suffix rule and the fact that `install`/`uninstall` manage them.

Internal: unit file contents, hardening directives, cron line syntax and install paths. These may
change between releases to improve security or portability.

### Release assets

Public:

- asset names: `jealous-vault-linux-amd64`, `jealous-vault-linux-arm64`,
  `THIRD-PARTY-LICENSES.md`, `SHA256SUMS`, `SHA256SUMS.sig`;
- `SHA256SUMS` covers the two binaries and the licences file;
- signatures use the SSH signature namespace `jealous-vault-release` and the identity `release`;
- release tags are the bare version, without a `v` prefix: `0.1.0`.

Changing these names, the checksum scope or the signature namespace is breaking for install scripts
and package builders.

### Platforms and requirements

The supported platform matrix and the tested limits live in
[docs/platforms-and-limits.md](docs/platforms-and-limits.md). Dropping a supported platform or
raising the minimum restic, Go or OS version is breaking. Adding a platform is not.

## Deprecation policy

1. The change is described in `CHANGELOG.md` and, for config or CLI, in `docs/`.
2. The old form keeps working for at least one `MINOR` release where technically possible.
3. A warning is printed when the old form is used, if a warning can be produced safely.
4. Removal happens in the next `MAJOR` release, or in the next `MINOR` release before `1.0.0`.

Examples:

- a renamed flag is kept as an alias for one minor release;
- a renamed config key is accepted with a deprecation warning for one minor release;
- a renamed unit gets a compatibility alias during the same window.

## What counts as breaking

Breaking:

- renaming or removing a command, flag or documented value;
- changing the meaning or default of a config key in a way that changes what is backed up;
- rejecting a config that a previous release accepted;
- removing or renaming a documented state, history or audit field;
- renaming a systemd unit or changing the job suffix rule;
- renaming a release asset or changing the signature namespace;
- dropping a platform or raising a minimum requirement.

Not breaking:

- adding a command, flag, config key or JSON field;
- changing error text, log format, alert wording or HTML;
- changing internal packages, temp file names or unit file contents;
- changing documentation, website or CI internals.

## Changing this contract

Architectural changes are recorded as ADRs in [docs/adr/](docs/adr/README.md). A change to this
document needs a changelog entry and, for anything that affects users, a note in the release.
